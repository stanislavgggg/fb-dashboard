# Кабинеты FB — сводный дашборд

Один экран для всех рекламных кабинетов Facebook, которые берутся у разных агентств и поставщиков. Сервис по расписанию ходит в каждый профиль агентства через его же прокси, забирает статистику по кампаниям и сводит её с регистрациями и депозитами из Keitaro по ID кампании. На выходе видно расход, реги, депы, цену рега и депа, доход, профит и ROI — по поставщику, байеру, профилю, кабинету, кампании или по дням.

## Что внутри

- **backend/** — FastAPI + SQLAlchemy (Postgres на проде, SQLite локально), планировщик синхронизации, алерты в Telegram, тесты.
- **frontend/** — React + TypeScript + Vite. Собирается в статику, которую отдаёт тот же бэкенд.
- **Dockerfile** — собирает всё в один контейнер для Railway.

### Как это работает

1. **Профиль** — один доступ от агентства: токен и прокси, через который байер заходит в этот профиль. Все кабинеты, видимые этому токену, подтягиваются сами.
2. Каждые 30 минут сервис пересобирает статистику Facebook за последние 7 дней. Окно перезаписывается целиком, поэтому поздние корректировки Facebook подхватываются и ничего не дублируется.
3. Keitaro отдаёт отчёт по дням и по `sub_id_1` (или другому параметру), в который из ссылки объявления приходит `{{campaign.id}}`. По нему конверсии привязываются к кампаниям. Всё, что не привязалось, показывается отдельным блоком **Conversions without an FB campaign**. Keitaro привязывает регистрацию и депозит к дню клика, поэтому его окно шире — 45 дней (`KEITARO_DAYS_BACK`), и оно тянется при каждой синхронизации, включая добавление нового профиля. Если через тот же Keitaro идёт другой трафик, задай `KEITARO_TS_ID`, чтобы чужие кампании не попадали в **Conversions without an FB campaign**.
4. Расход в EUR и других валютах переводится в доллары по курсам из настроек.

### Алерты в Telegram

- Токен профиля перестал работать.
- Прокси профиля не отвечает два запуска подряд.
- Кабинет отключили или он снова активен.
- Кабинеты пропали из профиля (агентство забрало доступ).
- Кампания потратила за сегодня больше порога, а регистраций 0.
- Кабинет подошёл к лимиту расходов.

Повторы одного и того же алерта за день не шлются. Если разом умерло много кабинетов, всё уходит одним дайджестом (несколькими сообщениями, если не влезает в лимит Telegram). Алерты старше суток, накопившиеся пока чат не был указан, в чат не льются.

### Что учтено

- Умерший токен, недоступный прокси, ошибка одного кабинета — не ломают синхронизацию остальных. Ошибка видна у профиля или кабинета.
- Лимиты API Facebook (коды 4, 17, 32, 613) — запрос ждёт и повторяется.
- Падение Keitaro не стирает данные Facebook.
- Кабинет, который агентство забрало, помечается **No access**, а не пропадает вместе с историей.
- Рестарт сервиса посреди синхронизации — зависший запуск закрывается сразу при старте, следующая синхронизация не ждёт.
- Facebook внезапно вернул 0 кабинетов — кабинеты не помечаются **No access**, профиль получает ошибку, ждём следующего запуска.
- Один кабинет виден двум профилям — он остаётся за первым активным профилем, статистика не прыгает между ними.
- Пароль прокси с `@`, `:` или `#` — понимается правильно (форматы `host:port:user:pass`, `user:pass@host:port`, `http://…`, `socks5://…`).
- **Today** для алертов и колонки **Spend today** считается по часовому поясу кабинета, а не сервера.
- Токены и прокси хранятся в базе зашифрованными, в интерфейсе видны только маскированными. Если сменить `SECRET_KEY`, раздел **Profiles** продолжает открываться и показывает, какие токены нужно ввести заново.
- Вход по логину и паролю, роли **Admin** и **Viewer**, защита от перебора паролей. Смена пароля (своя или через админа) разлогинивает остальные устройства.
- У пользователя **Viewer** можно указать байера — тогда он видит только профили, кабинеты, статистику и алерты этого байера (по полю **Buyer** у профиля). Фильтр по байеру для него принудительный, блок **Conversions without an FB campaign** скрыт, журнал запусков показывает только статусы.
- Курсы валют подтягиваются раз в день автоматически (ЕЦБ через Frankfurter, api.frankfurter.dev) для всех валют, которые встречаются на кабинетах. Ручной курс в настройках имеет приоритет — для валют, которых нет у ЕЦБ, или если нужен фиксированный. Авто-обновление можно выключить.
- Новые колонки в моделях добавляются в существующую базу автоматически при старте.

## Деплой на Railway

1. Залей репозиторий на GitHub и создай в Railway новый проект из этого репо. Railway сам найдёт `Dockerfile`.
2. Добавь в проект **Postgres**.
3. В переменных сервиса задай:
   - `DATABASE_URL` = `${{Postgres.DATABASE_URL}}`
   - `SECRET_KEY` — сгенерируй один раз командой ниже и сохрани в надёжном месте. Если его потерять, сохранённые токены придётся вводить заново.
     ```
     python -c "from cryptography.fernet import Fernet; print(Fernet.generate_key().decode())"
     ```
   - `ADMIN_LOGIN`, `ADMIN_PASSWORD` — первый админ.
   - `KEITARO_URL`, `KEITARO_API_KEY`, `KEITARO_CAMPAIGN_SUB`.
   - `TG_BOT_TOKEN` — если нужны алерты.
4. Сгенерируй домен в Settings → Networking и зайди под админом.
5. В разделе **Profiles** добавь доступы агентств. Кнопка **Check access** покажет, видит ли токен кабинеты через этот прокси. После сохранения подтянется статистика за 30 дней.
6. В **Settings** укажи ID чата для алертов; курсы валют подтянутся сами после первой синхронизации (или кнопкой **Update now**). Кнопка **Send test** работает с ID, который вписан в поле, сохранять не обязательно.
7. У кабинетов можно проставить гео (**Ad accounts** → **Edit**) — после этого в сводке появится группировка и фильтр по гео.

Остальные переменные — в `.env.example`.

### Обязательно в объявлениях

Чтобы реги и депы привязались к кампаниям, в ссылке каждого объявления должен быть параметр с ID кампании, например:

```
https://your-keitaro.domain/xxxx?sub_id_1={{campaign.id}}&sub_id_2={{adset.id}}&sub_id_3={{ad.id}}
```

В Keitaro регистрация должна приходить постбеком со статусом `lead`, депозит — `sale`.

## Локальный запуск

```bash
# бэкенд
cd backend
pip install -r requirements-dev.txt
cp ../.env.example .env        # заполни SECRET_KEY и ADMIN_PASSWORD, COOKIE_SECURE=0
python -m app.demo             # необязательно: демо-данные, чтобы посмотреть интерфейс
uvicorn app.main:app --reload --port 8000

# фронтенд (второй терминал)
cd frontend
npm install
npm run dev                    # http://localhost:5173, /api проксируется на :8000
```

Тесты: `cd backend && pytest`.

Догрузить историю за 90 дней разом: `python -m app.sync --days 90` (или кнопка **Run** в **Sync**).

## Проверка здоровья

Одна проверка смотрит всё сразу: база, планировщик, когда была последняя синхронизация и чем закончилась, не завис ли запуск, умершие токены и прокси, профили, которые давно не обновлялись, кабинеты с ошибками, свежесть данных Keitaro, курсы валют и доходят ли алерты до Telegram. У каждого пункта уровень `ok`, `warn` или `fail`.

**Из терминала** (нужна переменная `HEALTH_TOKEN`, сгенерировать: `openssl rand -hex 24`):

```bash
curl -s -H "X-Health-Token: ТВОЙ_ТОКЕН" "https://твой-домен.up.railway.app/api/health?format=text"
```

Без `?format=text` вернётся JSON. Ответ `200`, если всё в порядке или есть только предупреждения, и `503`, если что-то сломано.

**Внутри контейнера** (Railway CLI: `railway ssh`, или локально):

```bash
python -m app.health          # текстом
python -m app.health --json   # JSON
```

Код выхода: `0` — всё в порядке, `1` — предупреждения, `2` — проблемы. Удобно для cron и скриптов. Состояние планировщика эта команда не видит (он живёт в процессе сервиса) — для него используй HTTP-вариант.

**В интерфейсе**: **Sync**, блок **Service health** (только для админа).

**Мониторинг аптайма**: в UptimeRobot, Better Stack и аналогах создай HTTP-монитор на `https://твой-домен/api/health?token=ТВОЙ_ТОКЕН` с ожиданием кода 200 — он пришлёт уведомление, когда проверка вернёт 503. `/healthz` для этого не подходит: он отвечает «жив ли процесс» и нужен Railway для деплоя.

## Важно знать

- **Токены агентских профилей живут ограниченное время.** Когда токен умирает, профиль подсвечивается красным и приходит алерт — нужно взять новый и вставить в **Edit**.
- **Часовые пояса.** Facebook считает день по часовому поясу кабинета, Keitaro — по `KEITARO_TZ`. В разрезе **By day** возможен небольшой сдвиг у кабинетов в другом поясе. В итогах за период всё сходится. У кабинетов в американских поясах «сегодня» начинается около 09:00 по Мадриду — до этого их расход за сегодня честно нулевой.
- **Курсы валют.** Обновляются автоматически раз в день; если источник недоступен, остаются прошлые, а в журнале запуска появится строка `rates not updated`. Сводка напомнит, если курсы не обновлялись больше 45 дней.
- **Один экземпляр сервиса.** Планировщик работает внутри процесса, поэтому в `railway.json` стоит одна реплика и один воркер.
